# 微信意图解析 · 模型输入/输出说明

> 对象：本地 Kev（System One 兼容）决策模型服务
> 端点：`POST http://127.0.0.1:8009/v1/systemone`（模型 `kev-latest`）
> 代码位置：`watcher.py` — `call_kev()` 发请求、`questions_for_chat()` 选问题集、`shape_result()` 整理响应

---

## 1. 整体链路

```
微信通知 → watcher 提取 (会话名, 原文)
        → questions_for_chat() 决定用「通用问题集」还是「会话专用问题集」
        → call_kev() POST 三件事：意图 / 紧急度 / 是否等我回复
        → shape_result() 整理 answers
        → 写 events.jsonl + 系统弹窗（+ 指定意图时飞书转发）
```

三问在服务端拼成**一条 token 序列、一次前向**完成（不是三次调用），实测单次约 0.3~1.5 s。

---

## 2. 输入（HTTP 请求）

```http
POST /v1/systemone HTTP/1.1
Content-Type: application/json
Authorization: Bearer ***     ← KEV_API_KEY（环境变量或 ~/kev/.env；本地服务默认 "local"）
```

### 2.1 Body 结构

```json
{
  "state": "微信新消息\n来自：实时AI快讯 5群\n内容：群主不在就找我: 🚀 AGI Hunt 快讯 | 10 月 6 日 8 时\n\n……",
  "questions": { "intent": {…}, "urgency": {…}, "need_reply": {…} },
  "model": "kev-latest"
}
```

| 字段 | 说明 |
|---|---|
| `state` | 固定三行模板：`微信新消息` / `来自：<发送者或群名>` / `内容：<通知正文>`。群消息的正文自带 `发送者: ` 前缀；图片/语音/文件是占位文本（`[图片]` 等） |
| `questions` | 三道题的完整定义（见下），决定模型"看到什么选项" |
| `model` | 模型名，透传给服务 |

### 2.2 三种题型

| 题型 | type | 通用版定义位置 | 说明 |
|---|---|---|---|
| 意图分类 | `choice` | `questions.intent`，13 选 1 | 选项 = `criteria` 的键；值（描述）以 `标签: 描述` 拼进模型输入——**描述是命中率的关键**（裸标签 56% → 带描述 88%） |
| 紧急度打分 | `score` | `questions.urgency`，0~N 连续分 | `criteria` 是从宽到严排列的档位描述，服务端据此生成 `legend`（分值→档位名） |
| 等我回复吗 | `noul` | `questions.need_reply`，true/false | 二值判断，输出概率 |

服务端渲染（`kev.api.to_record`）：state 拉平为前缀，每题渲染成 `instr + 选项列表`，三题分支共享 state 前缀一次前向。诊断工具 `show_payload.py` 可打印完整渲染文本和 token 序列。

## 3. 通用问题集（默认，所有未被覆盖的会话）

### 3.1 `intent` — 13 类（`choice`）

指令（instr）：「这条微信消息最核心的意图是什么？先看有没有需要我做的事或等我回答的问题，再细分……能归入某类时不要选『其他』。」

| # | 标签 | 描述（发给模型的原文） |
|---|---|---|
| 1 | 问候寒暄 | 打招呼、问候、早安晚安、报平安 |
| 2 | 闲聊分享 | 分享日常、见闻、心情、吐槽，不指望我具体回应 |
| 3 | 提问求助 | 向我问信息、请我帮忙；「你在忙吗」「中午吃什么」这类要我接话的问句也归这里（问看法、评价、建议的归「征求意见」） |
| 4 | 征求意见 | 问我的看法、评价或建议（「你觉得…」「…怎么样」「行不行」） |
| 5 | 约时间安排 | 约见面、问我有没有空、定时间或改时间 |
| 6 | 事务通知 | 告知我某件事、进度或状态，一般不用回 |
| 7 | 工作交代 | 工作上布置任务、交代事项；工作场景里转达要我办的事（如「王总让你…」） |
| 8 | 催办紧急 | 催促、强调紧急、要我尽快或马上处理 |
| 9 | 发文件链接 | 发来文件、资料、链接让我处理或查看 |
| 10 | 分享内容 | 转发文章、视频、音乐等内容给我看 |
| 11 | 红包转账 | 红包、转账、收款相关的消息 |
| 12 | 表达情感 | 关心、想念、感谢、道歉等情感表达 |
| 13 | 其他 | 无法归入以上任何一类 |

### 3.2 `urgency` — 3 档（`score` 0/1/2）

| 档位 | 描述 |
|---|---|
| 完全不用急 | 闲聊、分享类，看到也不用特地回 |
| 有空回一下 | 常规事项，今天内回复就行 |
| 尽快处理 | 对方在等结果、有事相求或催办，最好马上回 |

### 3.3 `need_reply` — 2 项（`noul`）

- `false`：不是，对方只是告知或分享，不回复也可以
- `true`：是，对方在等我的回应

## 4. 非通用：会话专用问题集（`chat_overrides`）

### 4.1 覆盖机制（`questions_for_chat`）

- 配置在 `config.json` 的 `chat_overrides`：`{"会话名关键字": {"问题名": {补丁字段}}}`
- 匹配规则：**会话名包含关键字即命中**（如 `爱人` 匹配 `爱人（备注）`）；**首个命中的关键字生效**，多个不叠加
- 合并方式：**按题浅合并**——只替换被补丁的字段（如 `intent` 整体换掉、`urgency.criteria` 换掉），未提及的题（如 `need_reply`）**原样继承通用版**
- 典型用法：亲密联系人把"工作类"意图换成"情感类"意图、3 档紧急度细化为 5 档

### 4.2 现网示例：「爱人」专用集

`intent` 换成专用 13 类（指令强调「先判断她是不是在要我的关注或回应，再归具体类别」）：

| # | 标签 | 描述（摘要） |
|---|---|---|
| 1 | 撒娇讨关注 | 撒娇、卖萌、讨哄求关注（「哼」「不理你了」）；说难受、好累、想被关心也算 |
| 2 | 情感表达 | 爱你、想你、感谢、道歉这类直白的情感话 |
| 3 | 闲聊分享 | 分享日常、见闻、好玩的事、吐槽 |
| 4 | 提问求助 | 问我信息、请我帮忙、要我拿主意；跟约会相关的商量归「约时间安排」 |
| 5 | 征求意见 | 问我的看法、评价 |
| 6 | 约时间安排 | 约会见面、问有没有空、定或改时间；商量约会去哪玩也算 |
| 7 | 生活琐事 | 家里的事要我办或问我办了没（买东西、快递、接送） |
| 8 | 情绪不满 | 生气、委屈、抱怨、暗示我做得不好 |
| 9 | 催问回复 | 催我回话或问我怎么还没回 |
| 10 | 分享内容 | 转发文章、视频、音乐、链接给我 |
| 11 | 红包转账 | 红包、转账、收款有关的消息 |
| 12 | 事务告知 | 告知我她的行程、状态、安排 |
| 13 | 其他 | 无法归入以上任何一类 |

`urgency` 换成 5 档（`score` 0~4）：看完就好 → 看到回一下 → 今天内回 → 尽快回 → 马上回。
`need_reply`：**不覆盖，与通用版相同**。

效果（18 条标注样本实测）：通用 7/18（38.9%）→ 专用 15/18（83.3%）。

## 5. 输出（响应）

### 5.1 原始结构

```json
{
  "answers": {
    "intent":     { "type": "choice", "choice": "事务通知", "confidence": 0.2523,
                    "probabilities": { "问候寒暄": 0.0162, "闲聊分享": 0.1398, "提问求助": 0.0701,
                                       "征求意见": 0.0195, "约时间安排": 0.0038, "事务通知": 0.3098,
                                       "工作交代": 0.0437, "催办紧急": 0.0118, "发文件链接": 0.0348,
                                       "分享内容": 0.1343, "红包转账": 0.0032, "表达情感": 0.0051,
                                       "其他": 0.208 } },
    "urgency":    { "type": "score", "score": 0.7265, "confidence": 0.2537,
                    "probabilities": { "0": 0.3855, "1": 0.502, "2": 0.112 },
                    "legend": { "0": "完全不用急：…", "1": "有空回一下：…", "2": "尽快处理：…" } },
    "need_reply": { "type": "noul", "noul": 0.1168 }
  },
  "latency_ms": 483
}
```

> 上例为真实线上输出（「实时AI快讯 5群」的一条快讯，通用问题集）。

| 字段 | 含义 |
|---|---|
| `choice` | 意图题的选项标签（13 类之一） |
| `score` | 紧急度的**期望分**：Σ(档位值 × probabilities[该档])；watcher 定档 = `round(score)` 后查 `legend`（专用 5 档时 legend 有 5 项） |
| `noul` | need_reply 的输出即 P(对方在等我回复)，**>0.5 判「是」**（阈值硬编码在 `notify()`：`nr > 0.5`）；无 confidence/probabilities 伴随字段 |
| `confidence` | 模型对该答案的自信度（0~1）；实测错误样本几乎都在 <0.6 区间 |
| `probabilities` | 全选项分布；`score` 题是各档位概率 |
| `latency_ms` | 服务端推理耗时 |

### 5.2 怎么判读：score 与 noul（以 5.1 的真实输出为例）

**score —— 看期望值定档，probabilities 看摇摆程度**

- `score = Σ(档位值 × 该档概率)`：本例 `0×0.3855 + 1×0.502 + 2×0.112 = 0.726` ≈ `score 0.7265`
- 定档规则（watcher `shape_result`）：`round(0.7265) = 1` → 查 `legend["1"]` → **「有空回一下」**
- 本例 P(1)=0.502 与 P(0)=0.386 贴得很近 → 模型在「完全不用急 / 有空回一下」之间犹豫（confidence 仅 0.2537 也印证），期望分于是落在两档之间偏上
- **极端情况期望档 ≠ argmax 档**：如 P=(0.45, 0.30, 0.25)，概率最大的档是 0，但期望 = 0.80 → 定档 1。watcher 采用**期望档**（对中间档更平滑、不跳变）
- 使用建议：展示取 `label` 即可；要过滤低把握就同时看 `confidence`（实测 <0.4 基本不可信，错误样本几乎都在 <0.6 区间）

**noul —— 本身就是概率，直接和 0.5 比**

- `noul = 0.1168` 即 P(对方在等我回复) → 远低于 0.5 → **不等回复** ✓（本例是群发快讯，合理）
- 判「是」（>0.5）时弹窗正文加 `⚑等你回复` 前缀
- 没有 confidence/probabilities 伴随字段——输出的数字本身就是概率语义，**离 0.5 越远越确定**；贴近 0.5 就是模型拿不准

### 5.3 watcher 内部形态（`shape_result` 之后，写入 events.jsonl）

### 5.2 watcher 内部形态（`shape_result` 之后，写入 events.jsonl）

```json
{
  "intent":     { "value": "事务通知", "confidence": 0.2523, "probabilities": {…} },
  "urgency":    { "value": 0.7265, "label": "有空回一下", "confidence": 0.2537,
                  "probabilities": {…}, "legend": {…} },
  "need_reply": { "value": 0.1168 }
}
```

差异：`choice`/`noul` 统一成 `value`；`score` 额外带 `label`（按 legend 换算的短档位名，如「有空回一下」）。

### 5.4 下游使用

- 系统弹窗：标题 `微信意图 · <intent> · <urgency.label>`，`need_reply>0.5` 时正文加 `⚑等你回复`
- 飞书转发：`intent ∈ {发文件链接, 分享内容}` 时经 lark-cli bot 私聊推送 `[<intent>] <会话>\n<原文>`
- `events.jsonl` 每条事件带 `ts / chat / text / sender / source / result / latency_ms` 全量留存
